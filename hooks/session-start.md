# APD: コードを書く前に設計の区分を決める

ユーザーから何かを作る・変える依頼を受けたら、コードを書く前（ファイルを探索する前でもよい）に、どの区分かを決めて 1 行で宣言する。ユーザーが「Spec にして」「Plan でいい」「設計なしで」と指定したらそれに従う。

| 区分 | 対象 | 進め方 |
|---|---|---|
| Design | 新しいプロダクト、大きな方向転換 | `apd:design` skill |
| Spec | 外から見える振る舞いが変わる（新機能・仕様変更）。AC が書ける | `apd:spec` skill |
| Plan | 振る舞いは変わらない、または Spec にするほどでない変更（リファクタ、内部の技術変更、開発基盤・infra・設定、スクリプト、複数ファイルの修正） | `apd:plan` skill |
| 設計なし | typo、設定値の変更、数行の修正、原因と直し方が 1 つに決まるバグ修正 | そのまま実装 |

- Design / Spec / Plan は、ユーザーの承認を得るまでコードを書かない。設計の段階では不明点を質問して止まってよい
- 承認（「この方向で実装して」等）を得たら、実装・テスト・PR まで止まらずに進める。`/goal` やコマンドの入力をユーザーに求めない
- 雑談・調査・質問への回答・レビューなど、何も作らない依頼には適用しない
- サブエージェントとして委譲された作業には適用しない（設計は親が済ませている）
